# Map Graph and Routing Tests

Source: `src/lib/map/map-graph.test.mjs`.

esbuild-loads production TypeScript modules and exercises pure state, ELK layout, routing geometry, determinism, and performance.

## Helpers and fixtures

- `loadTypeScript(relativePath)` — esbuild-based module loader.
- `buildFixtureProject`, `ROUTING_FIXTURES`, `routingFixtureBySlug` — loaded from [`routing-fixtures.ts`](routing-fixtures.ts.md); the deterministic stress-graph fixtures shared with the on-disk debug workspace generator.
- `computeRoutingCost`, `routingAbsoluteRectangles` (imported as `absoluteRectangles` from [`routing.ts`](routing.ts.md), aliased here to avoid colliding with this file's own `absoluteRectangles(layout)` helper below, which has a different signature) — phase 5's routing-quality scorer and the document-rectangle helper it needs.
- `measureLayoutCost(layout)` — the phase-5 test-side adapter from one `MapLayout` (from `layoutMapGraph`) to `computeRoutingCost`'s inputs: builds a `Record<linkId, MapRoute>` straight from `layout.edges` (each edge's `data` is a structural superset of `MapRoute`) and a `Record<documentId, MapRect>` via `routingAbsoluteRectangles(layout.nodes)` filtered to document-kind nodes. Mirrors `elk-layout.ts`'s own internal `measureLayoutCost` exactly, but is an independent reimplementation from the same exported primitives (test code should not import a production module's non-exported internals) — used by the three phase-5 feedback-loop cases below.
- `hubCornerFraction(layout, hubId)` — an independent placement oracle for the hub-reorder fix: over every document node, finds the layer's own y-extent (min/max `y` via `routingAbsoluteRectangles`) and returns how far the named hub sits from that extent's midpoint as a `0..1` fraction of its half-span (`0` is dead center, `1` is pinned at the extreme edge). Unlike `computeRoutingCost`, this is a pure relative-position measure spacing changes alone cannot move, so an improvement in this fraction is directly attributable to degree-based model-order placement rather than the spacing sweep.
- controllable layout job `start()` / `cancel()` — cancellation oracle.
- `nestedProject`, `syntheticProject`, `fanProject`, `document`, `link` — deterministic ProjectModel-shaped graph fixtures.
- `duplicateNameProject(areaCount,modulesPerArea)` — large deterministic fixture with one document per nested area/module folder, filenames drawn from a small repeating pool (`REPEATED_DOCUMENT_NAMES`) so identical names recur across different folders; links include an in-area chain, cross-area links between same-named documents, and interleaved unresolved links.
- `oracleConnections(graph)` — per-document one-hop neighbor `Set`, derived directly from `MapGraph.links`, independent of the code under test.
- `event` — edge-trace event builder.
- `assertOrthogonal`, `absoluteRectangles`, nested `positionFor`, `routeIntersectsRect`, `assertAvoidsDocumentInteriors` — geometry assertions.
- `sideFromHandle(handle, prefix)`, `movesTowardSide(from, to, side)` — parse a `source-<side>-<index>`/`target-<side>-<index>` handle (built by `elk-layout.ts`'s `mapHandleId`) into a `MapSide`, and check a point pair moves in that side's direction; used by `assertValidArrowAndPorts`.
- `assertExplicitPortModel(layout, slug)` — cross-checks every edge's `data.sourcePort`/`data.targetPort` against its route geometry and handle: correct `direction`/`documentId`/`linkId`, `point` matching the route's own first/last point, `offset` inside `[0,1]`, and `id`/handle agreement; and, per document, that every port sharing one `side` has a distinct `index` covering `0..count-1` with no gaps, regardless of `direction` — the "ports phase" invariant `map-graph.test.mjs`'s previously-`skip`ped port-model test now asserts for real.
- `assertSpatialPortOrder(...)` — for a set of ports on one node/side, checks that `index` order is non-decreasing in the perpendicular position of each port's counterpart node, i.e. spatial neighbor order is preserved along that side.
- `ancestorIds`, `expectedBoundaryIds`, `assertFolderGatewayPolicy` — hierarchy/gateway oracle.
- `positions(layout)` — deterministic node-position projection.
- `routableGraph(folders, documents, links)`, `routableDocument`, `routableLink` — minimal `MapGraph`/`RoutableMapNode` fixtures that call `routeMapLinks` directly, bypassing ELK; `routableGraph` accepts an array of folders (the first is the root) so fixtures can nest zones.
- `boundaryNoiseFixture` — reproduces a zone-router obstacle whose inflated boundary and lead point diverge by a floating-point ULP.
- `unroutableZoneFixture` — one genuinely unroutable zone (a port strictly enclosed by an unrelated obstacle) alongside one healthy link.
- `crossZoneReservationRollbackFixture` — a link that reserves a segment crossing from an inner zone into an outer one, then fails once it reaches the outer zone (its target is unrelatedly enclosed there), alongside a second link confined to the inner zone whose cheapest route exactly ties with an alternate one, so it is only decided by whether the doomed link's inner-zone reservation was released.
- `assertOrthogonalPoints` — orthogonal/finite point-list assertion shared by the fixtures above.

## Cases

- Body-only signature stability; visible burst coalescing; hidden deferral.
- Active-job cancellation, latest-only execution, retry/hide/signature transitions.
- Independent pointer/keyboard edge traces and current-layout-only controls.
- Resolved-link graph derivation and deterministic nested ELK flattening.
- 20-link fan-in/fan-out independent lanes.
- Ten cross-folder links through deterministic gateways.
- Dense 60-document/240-link finite orthogonal obstacle-safe routing.
- Routes a link whose lead point lands on the floating-point boundary of its own inflated obstacle (regression for `Unable to route inside`).
- Keeps unrelated links routable and logs a diagnostic when one zone is genuinely unroutable, instead of throwing.
- A doomed cross-folder link's reservations in a zone it successfully crossed are rolled back once it fails in a later zone, so a later link sharing that zone routes identically to a baseline where the doomed link never existed.
- Self-links and duplicate relations remain independent.
- 100/200 and 500/1000 document/link performance gates.
- 240-document/duplicate-filename regression: hovering the rightmost (and thus most left-neighbored) document must, against the `oracleConnections` oracle, mark exactly the hovered document `'active'`, its true one-hop neighbors `'connected'`, and every other document — including everything positioned to its left and every repeated-name document — `'muted'`; also proves a leftover unrelated edge trace collides (masks the hovered document, wrongly activates an unrelated one) until `clearMapEdgeTraceForDocument` resets it, and that moving the trace to a second document clears the first.
- Edge trace left behind by pointer vs. keyboard focus: `clearMapEdgeTraceForDocument` resets either source identically, producing the same oracle-matching highlighted set.
- Live edge trace survives an overriding document hover: with an edge's `focusedEdgeId` genuinely set, calling the production `resolveTracedEdge(state,documentTraceActive,layoutEdges)` — the same function MapView's reactive `tracedEdge` calls, not a reimplementation — with `documentTraceActive: true` makes `nodeEmphasis`/`edgeEmphasis` resolve purely from the document while `edgeTraceState.focusedEdgeId` stays untouched; calling `resolveTracedEdge` again with `documentTraceActive: false` against that same untouched state resolves back to the original edge with no new trace event.
- Flow unmount resets a stale document trace via `resetMapTraceOnFlowUnmount`, restoring immediate edge tracing on remount with no flush-first document required.
- Per-node unmount via `clearMapDocumentTraceIfActive`: a still-active document's trace is cleared when its own node is destroyed (`onlyRenderVisibleElements` unmounting an individual virtualized node without an `onblur`/`onpointerleave`); a stale destroy for a document that is no longer the active trace (the user already moved on to a different document before the destroy callback ran) leaves the new, genuinely active trace untouched.

### Deterministic stress-fixture assertions (routing/readability epic, phases 1–5)

Every case below runs against all or specific fixtures in [`routing-fixtures.ts`](routing-fixtures.ts.md) — the same specs `scripts/generate-map-fixtures.mjs` renders to the on-disk debug workspaces under `test-fixtures/map-routing/`. Phase 1 established the deterministic fixture/metric baseline; phase 2 adds the explicit `MapPort` model and high-degree fan-in/fan-out lane assignment on top of it, and turns the ports-phase invariant and the mixed-hub combined-distinctness metric from `skip`/diagnostic into real assertions. Phase 3 adds repeated direction chevrons and crossing/junction gap semantics on top of that, and turns the chevron-rendering and crossing-marker cases from `skip`/diagnostic into real assertions. Phase 4 adds shared routing corridors/highways and typed folder-boundary gateway regions on top of that (part B of phase 4 also makes gateway-region convergence real, extending the gateway-region case below with numeric coordinate-clustering assertions), and turns the two remaining `skip`-marked cases (a crossing inside a shared highway lane, and typed corridor/lane objects for a multi-edge boundary crossing) into real assertions; no case in this suite is `skip`-marked any longer. Phase 5 (this is the final phase) adds the bounded layout/routing feedback pass — see [`elk-layout.ts.md`](elk-layout.ts.md) and [`routing.ts.md`](routing.ts.md)'s `MapRoutingCost`/`computeRoutingCost` — and turns the incremental-change fixture pair's former diagnostic-only "baseline for the later layout-feedback phase" case into a real stability assertion, plus adds a dedicated feedback-loop case below.

- `assertRouteGeometry(edge)` — orthogonal, finite, and free of zero-length segments.
- `assertValidArrowAndPorts(layout, slug)` — every edge has an `arrowclosed` marker and a valid source/target side handle (`sideFromHandle`, parsing the `<direction>-<side>-<index>` format `elk-layout.ts`'s `mapHandleId` produces), and (`movesTowardSide`) the first and last points of `edge.data.points` actually move away from the source / into the target in the direction that handle side names — a real cross-check between the encoded side and the route's own geometry, not just presence.
- `assertExplicitPortModel(layout, slug)` — the phase-2 port-model oracle: every edge's `data.sourcePort`/`data.targetPort` has the right `direction`/`documentId`/`linkId`, a `point` matching the route's own first/last point, an `offset` in `[0,1]`, and a handle ID that agrees with `<direction>-<side>-<index>`; and, per `documentId:side` group, every port's `index` is unique and forms a contiguous `0..count-1` range with a matching `count` — regardless of whether the ports in that group are source-role or target-role. Run against every fixture inside the main determinism loop below, plus targeted at `mixed-hub` and `fan-converge`.
- `perpendicularCenter(rect, side)`, `assertSpatialPortOrder(layout, documentId, side, slug)` — an independent spatial-order oracle: collects every port on one node/side (either role) together with its counterpart node's perpendicular center, sorts by port `index`, and asserts those centers are non-decreasing — i.e. index order preserves neighbor spatial order, per the ports-phase acceptance criteria.
- `segmentsCross(...)`, `countRouteCrossings(edges)` — proper (non-parallel, non-touching-endpoint) orthogonal segment crossing detector, used to record a diagnostic baseline (or, for `fan-converge`, a loose upper-bound assertion); a real crossing is never itself treated as a hard fault.
- 'routes every deterministic stress fixture identically twice with finite, orthogonal, interior-safe geometry' — for every fixture in `ROUTING_FIXTURES`: lays it out twice and asserts identical node positions, edge points, _and_ `sourcePort`/`targetPort` objects (determinism), asserts `assertRouteGeometry`/`assertAvoidsDocumentInteriors`/`assertValidArrowAndPorts`/`assertExplicitPortModel`, and asserts the whole fixture set stays under a 60s bounded-layout-time budget (reported via `context.diagnostic`).
- 'routes the cross-folder highway and nested fixtures through ordered, hierarchy-correct boundary gateways' — runs `assertFolderGatewayPolicy` (the existing hierarchy/gateway oracle) against `cross-folder-highway`, `nested-to-external`, and `unrelated-near-corridor`.
- 'keeps both directions of the bidirectional corridor as independent, non-merged edges' — 20 edges, exactly two per left/right pair, and no two edges share identical point geometry: proves `elk.layered.mergeEdges: false` holds for opposite-direction edges between the same pair.
- 'groups dense same-direction and bidirectional traffic into deterministic shared corridors, without absorbing unrelated edges' — the phase-4 corridor-detection case: on `dense-corridor`, finds the single 20-lane corridor, asserts one shared `direction`, 20 distinct `laneIndex`es, 20 distinct `linkId`s, and that `computeRoutingCorridors` is deterministic across repeated calls on the same routes; on `bidirectional-corridor`, finds the single 20-lane corridor and asserts both travel directions are present (opposite-direction lanes stay distinguishable inside one shared corridor); on `cross-folder-highway`, finds the single 16-lane corridor; on `unrelated-near-corridor`, asserts `computeRoutingCorridors` returns exactly one corridor (the real 5-link one) and that none of its lanes belong to the fixture's unrelated `nearby/` chain — the density-threshold false-positive-rejection case named by the phase-4 spec.
- 'produces typed gateway region/lane objects for multi-edge and single-edge folder boundary crossings' — the phase 4 gateway-region case: on `cross-folder-highway`, `computeGatewayRegions` returns exactly 2 regions (one per folder boundary), each with all 16 crossing links laned `0..15` with no gaps, and is deterministic across repeated calls; on `nested-to-external`, asserts one single-member region per boundary the lone link actually crosses, and that the region set's `folderId`s exactly match that route's own `boundaryGateways` — a well-formed, single-lane gateway region even when only one edge crosses that boundary. Also the gateway-**convergence** regression added in phase 4: for each of `cross-folder-highway`'s two regions, reads every lane's actual crossing coordinate (via `absoluteRectangles`, the test file's own node-geometry helper) and asserts they stay distinct (no two edges literally coincide), every sorted-neighbor gap is small (`0 < gap <= 8`, i.e. `GATEWAY_LANE_OFFSET`'s 4px step plus slack), the full 16-lane span is `<= 64px`, and that span is under 15% of the folder boundary's own length — the concrete, numeric form of "a small number of well-positioned gateway regions" rather than "one arbitrary point per edge scattered across the whole border" (see `routing.ts.md`'s "Gateway convergence" section for why this is safe to assert: the coordinate is decided before `ZoneRouter` ever routes to it, so it is correct by construction, not a post-hoc shift).
- 'keeps inbound and outbound lanes on the mixed hub independently ordered, and collision-free combined across both directions' — the 8 outgoing and 8 incoming hub endpoints are each internally distinct, `assertExplicitPortModel` holds, **and** all 16 endpoints combined are asserted distinct (`routing.ts`'s merged, direction-independent `portKey` grouping is what makes this hold — an earlier per-direction grouping left 2 of the 16 colliding on this exact fixture), plus `assertSpatialPortOrder` on all four hub sides.
- 'routes the fan-converge fixture as an organized trunk with distinct per-target ports' — the phase-2 `20 → 5` stress fixture: 20 edges resolve to exactly 5 targets with 4 distinct incoming ports each, `assertExplicitPortModel` holds, and `countRouteCrossings` stays below the edge count (a loose "readable trunk, not a tangle" sanity bound, reported via `context.diagnostic`).
- 'measures real geometric crossings on the crossing-heavy fixture as a baseline for the later crossing-marker phase' — asserts geometry/interior invariants, then reports `countRouteCrossings` via `context.diagnostic` as a baseline for the future crossing-marker phase.
- 'measures layout stability across the incremental-change fixture pair, confirming the layout/routing feedback pass adds no extra movement when quality is already good' — asserts `incremental-base` lays out identically across two runs (determinism), then lays out `incremental-next` (`incremental-base` plus one document and one link) and reports, via `context.diagnostic`, how many shared node IDs kept an identical position (still a measured metric, not a hard bound — the underlying ELK layered algorithm's own node reordering on a locally-edited graph is a pre-existing, phase-5-independent behavior this suite does not attempt to fix). What phase 5 adds as a real assertion: `measureLayoutCost` on both `incremental-base` and `incremental-next` reports `structural: 0`, proving the bounded feedback loop never actually engages (stays at its single, unadjusted first pass) for this exact pair — the phase-5 mechanism itself contributes zero additional movement on top of whatever ELK's own reordering already produced.
- 'reduces routing cost through the bounded layout/routing feedback pass on a deliberately poor initial layout' — the phase-5 case proper, on the new `dense-skip-chain` fixture (18 documents, one folder, a sequential chain plus 4-ahead skip links, deliberately dense enough that a single unadjusted ELK pass produces real crossings): lays it out once with `{ maxIterations: 1 }` (an explicit single-ELK-pass baseline) and once with the default (bounded, up to 3-iteration) feedback loop, asserts the feedback pass's `computeRoutingCost` `total` is never worse and its `structural` component is strictly lower than the single-pass baseline's — the concrete "quality metric improves after the feedback pass vs. a single ELK pass" acceptance criterion — then asserts the feedback pass itself is fully deterministic across two more repeated runs (identical node positions and identical route points) and still satisfies every base geometry/port invariant (`assertRouteGeometry`, `assertAvoidsDocumentInteriors`, `assertValidArrowAndPorts`, `assertExplicitPortModel`).
- 'moves a high-degree hub out of a bad corner through degree-based model-order placement, not spacing alone' — the code-review follow-up fix for the dead `elk.priority` hint (see [`elk-layout.ts.md`](elk-layout.ts.md)'s "High-degree hub bias" section): on the new `hub-in-corner` fixture, lays out once with `{ maxIterations: 1 }` and once with the default feedback loop (which now includes `attemptHubReorder`), and asserts three things the dead hint could never have proven: (1) the single-pass baseline actually pins the hub at an extreme layer edge (`hubCornerFraction > 0.9` — a fixture-validity check, not the fix itself), (2) the feedback pass moves that same fraction down by more than `0.3` — a placement-only measure spacing escalation cannot move on its own, isolating the hub-reorder mechanism specifically from the pre-existing spacing sweep, and (3) `computeRoutingCost`'s `total` and `structural` both improve, same shape as the `dense-skip-chain` case. Also asserts full determinism across two more repeated runs and every base geometry/port invariant, matching the `dense-skip-chain` case's rigor.
- `portModelFixture()` — a small hand-placed hub/A/B/C/D graph (bypassing ELK, via `routableGraph`/`routableDocument`/`routableLink`) where A/B/C link into the hub and the hub links out to D, all four sharing the hub's left side top-to-bottom in that order — a minimal, exact reproduction of the mixed-direction port congestion `mixed-hub` exercises at scale.
- 'assigns an explicit, structured port model to every route endpoint' — the former `skip`-marked ports-phase case, now real: runs `routeMapLinks` twice over `portModelFixture()` for determinism, checks every `MapPort`'s shape/range, confirms all four hub-side ports (3 target-role, 1 source-role) get distinct indices and a shared `count`, and calls `assertSpatialPortOrder` to confirm their ranked order matches A/B/C/D's declared top-to-bottom order.
- `rectNode(id, parentId, x, y, width, height)` — minimal `RoutableMapNode` builder shared by the phase-3 hand-placed fixtures below.
- `chevronRouteFixture()` — five independent, non-interfering links (bypassing ELK) engineered to specific route lengths/shapes: a short adjacent pair (route well under the chevron minimum length), a moderate horizontal gap, a very long horizontal gap, a tall vertical pair, and a diagonally-offset pair whose lead points cannot align, forcing an actual multi-segment bend.
- `chevronMatchesSegment(points, chevron)` — an independent oracle: finds which of a route's own segments a chevron's `point` lies on (by axis + strict interior range) and checks its `direction` matches that segment's own axis/sign, regardless of how many bends the route has.
- 'renders directional chevrons along each route, scaled by length and restrained on very long routes' — the former `skip`-marked chevrons-phase case, now real: over `chevronRouteFixture()`, asserts zero chevrons on the short route, a positive and non-decreasing count as routes get longer, a restrained (`<= 8`) count on the very long route, every chevron's direction validated by `chevronMatchesSegment` (including across the bend fixture's multiple segments), and that a purely horizontal/vertical route's chevrons are all `right`/`down` respectively.
- `assertCrossingGapsAreInterior(routes)` — an independent oracle used by the crossing-marker case: collects every route's own point coordinates as a set, then asserts no route's `crossingGaps` entry coincides with any of them — the geometric property that stands in for "no accidental junction marker," since a real junction would have to sit exactly on a shared endpoint.
- `crossingFixture()` — two independent links (bypassing ELK), one a straight horizontal route and one a straight vertical route, hand-placed so their paths cross exactly once at a point interior to both.
- `multiCrossingFixture()` — a 2×2 grid of two horizontal and two vertical independent links (bypassing ELK), hand-placed so each horizontal route crosses each vertical route exactly once (four real crossings total), exercising the "several crossings" acceptance case.
- 'marks a crossing indicator only where two independent routes truly cross geometrically' — the former `skip`-marked crossing-marker-phase case, now real: on `crossingFixture()`, asserts the horizontal edge owns exactly one `crossingGaps` entry and the crossing vertical edge owns zero (the fixed horizontal-owns-the-gap convention); on `multiCrossingFixture()`, asserts each of the two horizontal edges owns exactly two gaps and each vertical edge owns zero; `assertCrossingGapsAreInterior` runs against both fixtures and then, as a broader regression, against every `ROUTING_FIXTURES` layout's real edges (most of which currently produce zero real crossings after ELK layout, `crossing-heavy` included, since ELK's own crossing-minimization already reorders nodes to avoid them — ports for the future router-preference phases to build on).
- `highwayCrossingFixture()` — four parallel same-direction row links (bypassing ELK), spaced 20px apart so they cluster into one shared corridor, plus one independent perpendicular link crossing straight through the middle of that corridor's shared band.
- 'marks a crossing indicator for a crossing occurring inside a shared highway lane area' — the former `skip`-marked highway/corridor-phase case, now real: on `highwayCrossingFixture()`, asserts all four row edges share one `corridor` (same `corridorId`, distinct `laneIndex`es `0..3`), the perpendicular crosser has no corridor of its own (a lone crosser never joins a parallel highway), each row edge still owns exactly one `crossingGaps` entry where the crosser intersects it, the crosser itself owns zero (unchanged horizontal-owns-the-gap convention), and `assertCrossingGapsAreInterior` holds — proving crossing-gap detection composes correctly with corridor membership rather than being disturbed by it, including now that corridor membership can move a member's own points via `applyCorridorLaneOffset`.
- `corridorThresholdFixture()` — a hand-placed fixture (bypassing ELK, via `routableGraph`/`rectNode`) combining a 3-link parallel row group (spaced 20px apart, at `CORRIDOR_MIN_MEMBERS`) with a separate 2-link parallel row group placed far enough away (`>CORRIDOR_LANE_GAP`) to never merge with the first, but only 20px apart from each other so the pair itself satisfies the pairwise adjacency test.
- 'requires at least CORRIDOR_MIN_MEMBERS parallel edges before they cluster into a corridor' — the dedicated `CORRIDOR_MIN_MEMBERS` threshold-boundary case the corridor-detection review defect asked for: on `corridorThresholdFixture()`, asserts the 3-link group clusters into one shared corridor with distinct `laneIndex`es `0..2`, asserts both 2-link "noise" routes keep `corridor: null`, and asserts `computeRoutingCorridors` returns exactly one corridor overall — proving the density threshold rejects an exactly-below-threshold coincidentally-parallel pair even when it independently satisfies every other corridor-adjacency test, distinct from the pre-existing `unrelated-near-corridor` case (which tests an unrelated, non-adjacent chain rather than a pair that _would_ cluster together if the count alone were enough).

"Stale and cancelled worker results never reach the UI" is already covered generically (not fixture-specific) by the existing layout-session/request-queue cases above (`exposes edge controls only for the current successful layout`, `cancels active layout work and starts only the latest queued job`, etc.); no new stress-fixture case duplicates it. Phase 5's now-potentially-multi-pass `layoutMapGraph` was re-verified against these same, unmodified cases rather than adding a phase-5-specific duplicate — see [`elk-layout.ts.md`](elk-layout.ts.md)'s "Cancellation and staleness" section for why one `layoutMapGraph` call is still exactly one cancellable unit of work regardless of its internal iteration count.
