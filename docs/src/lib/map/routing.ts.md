# Orthogonal Router

Source: `src/lib/map/routing.ts`.

Deterministic obstacle-aware router over absolute compound geometry. Allocates an explicit, structured `MapPort` per edge endpoint on the four document sides, folder-boundary gateways, independent lanes, Manhattan paths, and — as a post-processing pass over the finished geometry — shared routing corridors/highways and typed gateway-region groupings. Gateway-region detection stays purely a labeling pass; corridor detection also perpendicularly offsets each corridor member's own shared segment by a small, safety-gated amount, so corridor membership changes what is actually drawn rather than only what is labeled.

## Contracts

- `MapSide`, `MapPoint`, `MapRect` — geometry primitives.
- `MapBoundaryGateway` — one edge's folder/side/point crossing record, plus its resolved corridor membership at that crossing: `regionId` (the owning `MapGatewayRegion.id`), `laneIndex`/`laneCount` (this edge's rank and the total member count within that region). Constructed with placeholder `regionId: ''`/`laneIndex: 0`/`laneCount: 1` by `routeGateway`; `attachGatewayRegions` overwrites every gateway's placeholder with its real region assignment once all routes exist, so by the time `routeMapLinks` returns, every `MapBoundaryGateway` in every route always carries its final region/lane values.
- `MapGatewayLane` — one edge's membership in a `MapGatewayRegion`: `linkId`, `laneIndex` (0-based rank by position along the boundary side), `point`.
- `MapGatewayRegion` — one deterministic, well-positioned crossing point cluster for one folder+side boundary: `id` (`<folderId>:<side>:<index>`), `folderId`, `side`, `index` (0-based, ordered by the region's own position along the boundary), `point` (the cluster's centroid on the boundary), `lanes` (every edge crossing through this region, ordered by `laneIndex`).
- `MapCorridorAxis` — `'horizontal' | 'vertical'`, the shared travel axis of one `MapCorridor`.
- `MapCorridorLane` — one edge's membership in a `MapCorridor`: `linkId`, `laneIndex` (0-based rank by the lane's perpendicular position), `direction` (the `MapChevronDirection` of that edge's own segment inside the corridor, so opposite-direction traffic sharing one corridor stays distinguishable).
- `MapCorridor` — one detected shared routing corridor/highway: `id` (`corridor:<axis>:<index>`), `axis`, `band` (the perpendicular coordinate range spanned by its lanes), `extent` (the along-axis coordinate range the corridor's shared region covers), `lanes` (every member edge, ordered by `laneIndex`).
- `MapCorridorAssignment` — the corridor membership summary attached to one `MapRoute.corridor`: `corridorId`, `axis`, `laneIndex`, `laneCount`, `direction`.
- `MapPort` — the explicit, structured per-edge port model: `id` (`<documentId>:<side>:<index>`, unique within that node/side), `documentId`, `linkId`, `direction` (`'source' | 'target'`), `side`, `index`/`count` (this port's rank and the total port count sharing that node/side), absolute `point`, and `offset` (0–1 fraction along the side, for CSS placement without recomputing geometry). One `MapPort` exists per edge endpoint; there is no reserved/unused port, so an idle node side with no edges has none.
- `MapChevron` / `MapChevronDirection` — one small intermediate direction marker: an absolute `point` on the route and the `'up' | 'down' | 'left' | 'right'` facing of the segment it sits on.
- `MapRoute` — points, endpoint sides, `sourcePort`/`targetPort`, ordered gateways (each carrying its own region/lane), `chevrons` (repeated direction markers along this route), `crossingGaps` (points on this route's own path where it must render a small visual gap because another, unrelated route crosses it), `corridor` (this route's `MapCorridorAssignment`, or `null` when this route is not part of any detected corridor).
- `RoutableMapNode` — flow node geometry input.
- `RouteDescriptor`, `RankedMember`, `HeapEntry` — internal route/group/search records.
- `CorridorCandidate` — internal per-segment corridor-clustering record: `linkId`, `axis`, `perpendicular`/`start`/`end` coordinates, `direction`, and the exact `from`/`to` route points the segment came from (used to locate and offset that literal segment later).
- `BuiltCorridor` — internal pairing of one finished `MapCorridor` with the `Map<linkId, CorridorCandidate>` of exactly which segment was kept per member link, so `attachRoutingCorridors` can offset the same segment `buildCorridor` counted.
- `ZoneReservation` — a `ZoneRouter`/points pair recorded while one link's descriptor is being built, so a later failure in that same descriptor can undo exactly the reservations it made.
- `RouteUnavailableError` — thrown by `ZoneRouter.route` when a source/target pair has no path even after the relaxed-clearance retry; carries the zone `bounds` and the `source`/`target` points for diagnostics.

## Routing orchestration

- `routeMapLinks(graph, nodes)` — builds absolute geometry/descriptors, ranks port/gateway groups, routes each link through `routeDescriptor`, then — once every route exists — calls `attachGatewayRegions`, then `attachRoutingCorridors` (which, unlike phase 4's initial version, may itself adjust a corridor member's own points; see "Shared corridors and gateway regions" below), then recomputes every route's `chevrons` from its final (possibly lane-offset) points, then calls `attachCrossingGaps` last so its gap points are always derived from final rendered geometry. This order — geometry-mutating passes before the two geometry-*reading* readability passes — replaces phase 4's original `attachCrossingGaps` → `attachGatewayRegions` → `attachRoutingCorridors` sequence, which assumed neither region/corridor pass ever touched `points`. Returns an edge-ID map. A link whose zone routing throws (boundary-ascent mismatch or `RouteUnavailableError`) is skipped and reported via `reportUnroutableLink` instead of aborting the remaining links — one impossible edge never blanks the whole map.
- `routeDescriptor(...)` — builds one link's full point sequence (ports, gateway crossings, zone-router segments) and returns its `MapRoute`, with `chevrons`/`crossingGaps` left as `[]` and `corridor` left `null` until `routeMapLinks`'s later passes fill them in from final geometry; throws on the first unroutable segment. A cross-folder link can route cleanly through one or more zones - each successful `ZoneRouter.route()` call along the way reserving its segments in that zone - before failing in a later one; every `route()` call is recorded as a `ZoneReservation` as it succeeds, and if the descriptor then throws, all of that link's reservations are undone via `releaseReservations` before the error propagates, so a link that will never be rendered never leaves other links penalized for segments only it ever used.
- `routeSegment(router, source, target, reservations)` — thin wrapper around `ZoneRouter.route` used by `routeDescriptor` that also appends the call's router/points pair to the in-flight `reservations` list.
- `releaseReservations(reservations)` — calls `ZoneRouter.release` for every recorded reservation; used by `routeDescriptor`'s catch block to undo a failed link's partial progress.
- `reportUnroutableLink(descriptor, error)` — logs a `console.warn` diagnostic naming the link ID, its source/target documents, and its LCA zone.
- `segmentIntersectsRectInterior(source, target, rect)` — axis-aligned obstacle intersection predicate, tolerant of boundary points within `GEOMETRY_EPSILON` of a rect edge.
- `descriptorForLink(...)` — derives endpoint rectangles/sides, ancestor chains, LCA zones, and boundary sequence.
- `absoluteRectangles(nodes)` / nested `absolutePosition(id)` — flatten compound-relative node positions.
- `facingSides(source, target)` — chooses primary source/target sides.
- `boundaryChains(graph, sourceFolderId, targetFolderId)` — returns ordered ascent/descent gateway steps.
- `ancestors(graph, folderId)` — folder-to-root chain.
- `buildZoneRouters(...)` — creates one obstacle router per folder/root zone.

## Search structures

- `ZoneRouter.constructor(bounds, obstacles)` — initializes per-zone segment usage.
- `ZoneRouter.route(source, target)` — direct-route fast path, then visibility-grid Dijkstra with bend/shared-segment costs against the full-clearance obstacles; on failure, retries once against the same obstacles inset by the clearance amount (trading buffer for connectivity in tight zones) before throwing `RouteUnavailableError`.
- `ZoneRouter.attemptGridRoute(source, target, obstacles)` — builds the visibility grid and runs Dijkstra for one obstacle set; returns `null` instead of throwing when the target is unreachable.
- `ZoneRouter.pointValid(point, obstacles)` — bounds/obstacle test; bounds are checked with `GEOMETRY_EPSILON` tolerance so accumulated floating-point drift never misclassifies a boundary point as outside the zone.
- `ZoneRouter.segmentClear(source, target, obstacles)` — obstacle-interior test.
- `ZoneRouter.reserve(points)` — increments deterministic segment usage.
- `ZoneRouter.release(points)` — decrements (and, at zero, removes) the segment usage `reserve` recorded for `points`; the exact inverse, called by `releaseReservations` to undo a failed link's already-successful hops through this zone.
- `MinHeap.size` — queued entry count.
- `MinHeap.push(entry)` / `pop()` — stable binary min-heap for routing states.

## Floating-point tolerance

Lead/gateway points are constructed by moving a port outward by the same clearance amount used to inflate that document's own obstacle rectangle, so in exact arithmetic they land exactly on the obstacle's boundary. The two values are computed through different addition orders (`(x - clearance) + (width + 2 * clearance)` for the obstacle edge vs. `(x + width) + clearance` for the point), which can disagree by up to a few ULPs for large accumulated coordinates. `pointInsideRect` and `segmentIntersectsRectInterior` therefore treat a point within `GEOMETRY_EPSILON` (`1e-6`, far below any real layout spacing) of a rect edge as on the boundary, not inside — this is the fix for `Unable to route inside` on large graphs, where deep compound-position summation produces exactly this class of boundary drift.

## Lane and gateway allocation

- `buildPortGroups(descriptors)` / `buildGatewayGroups(descriptors)` — collect ranked members by physical region.
- `routeGateway(...)` — routes to/from one boundary point.
- `addRankedMember(...)`, `sortGroups(groups)`, `rankFor(groups,key,id)` — deterministic lane ordering.
- `portPoint(...)`, `gatewayPoint(...)`, `pointOnRect(...)` — convert rank to concrete border coordinate.
- `distributedOffset(...)` — spreads lanes within available span.
- `movePoint(point,side,distance)` — moves outward/inward by side.
- `buildMapPort(documentId,linkId,direction,side,rect,rank,point)` — assembles one `MapPort` from a resolved rank/point; called once per endpoint by `routeDescriptor`.
- `sideOffset(rect,side,point)` — converts an absolute border point back to a 0–1 fraction of that side's length, clamped; feeds `MapPort.offset`.
- `portKey(documentId,side)` — the port congestion-group key: **only** `documentId`+`side`, deliberately not direction. `buildPortGroups` registers both a link's source-role and target-role membership under this key, so every edge touching one side of one node — whether it originates or terminates there — is ranked in a single shared sequence and gets a strictly distinct `index`/offset. This is what makes a high-degree node's combined incoming+outgoing boundary collision-free (see the `mixed-hub` fixture's 16 distinct endpoints): ranking source and target separately, as an earlier version of this router did, let an edge of one direction land on the exact point of an edge of the other direction whenever both independently chose the same side.

## Readability markers (chevrons and crossing gaps)

Pure, deterministic post-processing over already-routed geometry; neither step changes a single route's points, avoids a crossing, or reroutes anything - router preference for avoiding/rerouting a crossing is a later-phase concern (see Invariants below).

- `computeRouteChevrons(points)` — repeated intermediate direction markers along one route, independent of every other route. `routeLength` sums the route's own Manhattan segment lengths; below `CHEVRON_MIN_ROUTE_LENGTH` (96) the route renders none. Otherwise the usable span (`total - 2 * CHEVRON_END_MARGIN`, margin 24 on each end so markers never crowd a port or the final arrowhead) is divided into `count = clamp(floor(usable / CHEVRON_SPACING), 1, CHEVRON_MAX_COUNT)` evenly-spaced interior positions (spacing preference 64, hard cap 5) - this is what keeps a very long route's chevron count "restrained" rather than growing without bound. `pointAlongRoute` walks the point list by cumulative distance to place each chevron exactly on the segment it falls in and derive its `MapChevronDirection` (`chevronDirection`) from that segment's own axis and sign, so orientation is always correct on both horizontal and vertical segments, including across a multi-bend route.
- `attachCrossingGaps(routes)` / `computeCrossingGaps(routes)` / `recordRouteCrossings(...)` — after every link in the graph has a route, every pair of _different_ edges' segment lists is checked for a real geometric crossing via `segmentCrossingPoint`, which requires one segment horizontal and the other vertical and the intersection strictly interior to both (the same `GEOMETRY_EPSILON`-tolerant interior test style as `segmentIntersectsRectInterior`) - a shared endpoint (a port, a corner, a gateway point) is therefore never mistaken for a crossing. Ownership of the resulting gap is a fixed convention, not a per-instance choice: the edge whose segment is horizontal at that crossing always owns the gap, so a genuine connection (two segments only ever meeting exactly at a shared endpoint) can never accidentally render one. Each owning route's gap points are recorded with their cumulative distance along that route (so multiple gaps on one route are already caller-ready in path order) and deduplicated by coordinate.
- Crossing vs. junction: TraceDoc's router never intentionally joins two different links' geometry at an interior point - every edge is independently routed end to end - so a "genuine junction" (the explicit-marker case the parent issue describes) cannot occur under the current router and is not modeled as a distinct type; only the non-connected crossing gap exists today. `crossingGaps` staying empty for every edge in a fixture with zero real crossings, and never containing a point that coincides with any route's own endpoint list, is the invariant that stands in for "no accidental junction marker."
- Router preference (avoid the crossing, reroute the edge, or nudge the layout, before ever rendering a gap) is explicitly out of scope for this phase: `attachCrossingGaps` only renders a gap for whatever crossing the existing router output already contains: it never changes routing to reduce crossings.

## Shared corridors and gateway regions

Deterministic post-processing over already-routed geometry, run once by `routeMapLinks` after every route exists. Neither pass reroutes an edge, repositions a node, or changes ELK's layout decisions. `computeGatewayRegions`/`computeRoutingCorridors` are pure detection/labeling functions — exported standalone so a caller can recompute the same grouping directly from a `Record<string, MapRoute>` without re-routing — and never touch `points`. `attachGatewayRegions` stays pure metadata-only, matching phase 4's original design. `attachRoutingCorridors`, however, now also *renders* the grouping it detects: for a route whose corridor membership passes a battery of safety checks (below), it perpendicularly offsets that route's own shared-corridor segment by a small, deterministic, per-lane amount, so lanes that used to sit exactly on top of each other now occupy visually distinct, evenly-spaced parallel tracks. This is the fix for the phase-4 review defect: corridor/gateway metadata existing without ever changing what is actually drawn.

- `computeGatewayRegions(routes)` — groups every route's `boundaryGateways` entries by `folderId`+`side` (`gatewayKey`), then, within each group, sorts members by their coordinate along that boundary (`perpendicularCoordinate`) and splits into contiguous clusters wherever the gap to the previous member exceeds `GATEWAY_REGION_GAP` (40). Each cluster becomes one `MapGatewayRegion`, `index`ed in ascending-coordinate order; because the existing `gatewayPoint` lane allocation already tightly clusters every edge crossing one folder+side around a single window (spacing capped by `GATEWAY_SPACING`), a boundary crossed by many edges today resolves to exactly one region — "a small number of well-positioned gateway regions" per the routing corridors/gateways spec, never one arbitrary point per edge.
- `attachGatewayRegions(routes)` — calls `computeGatewayRegions`, then walks every route's `boundaryGateways` a second time and overwrites each gateway's placeholder `regionId`/`laneIndex`/`laneCount` with its resolved region membership. Still never touches `points` or a gateway's `point` — see "Gateway convergence was attempted and reverted" below for why.
- `perpendicularCoordinate(side, point)` — the coordinate along one boundary side (`point.y` for `left`/`right`, `point.x` for `top`/`bottom`) used to order and cluster gateway members, and to compute a corridor's per-lane offset direction.
- `computeRoutingCorridors(routes)` — thin wrapper over `computeBuiltCorridors` that discards its per-lane segment map and returns just the public `MapCorridor[]`; unchanged in behavior from phase 4's original version.
- `computeBuiltCorridors(routes)` — the shared engine behind both `computeRoutingCorridors` and `attachRoutingCorridors`'s offsetting: collects every route's own orthogonal segments as `CorridorCandidate`s (`collectCorridorCandidates`; segments shorter than `CORRIDOR_MIN_SEGMENT_LENGTH`, 24, are dropped so a port/gateway lead-in stub can never seed a corridor on its own — each candidate also keeps its exact `from`/`to` route points, not just derived coordinates, so a later offset can find and shift that literal segment), then clusters candidates of the same axis via union-find (`clusterCorridorCandidates`) wherever `corridorCandidatesAdjacent` holds: the two segments' perpendicular coordinates differ by at most `CORRIDOR_LANE_GAP` (24) **and** their along-axis ranges overlap by at least `CORRIDOR_MIN_OVERLAP` (32). A cluster only becomes a `MapCorridor` when it spans at least `CORRIDOR_MIN_MEMBERS` (3) _distinct_ links — this is the density threshold that keeps one or two coincidentally parallel short edges from ever registering as a highway (verified against both the `unrelated-near-corridor` fixture's independent nearby chain and the dedicated `requires at least CORRIDOR_MIN_MEMBERS parallel edges before they cluster into a corridor` boundary test in `map-graph.test.mjs`). `buildCorridor` dedupes a link that contributed more than one candidate to the same cluster down to its single longest segment (returning both the finished `MapCorridor` and the `Map<linkId, CorridorCandidate>` of exactly which segment was kept per member), ranks the survivors by perpendicular coordinate into `laneIndex`es, and derives `band`/`extent` from the member set; the finished corridor list is then sorted by `axis`, `extent.start`, and `band` for a fully deterministic `id`/ordering.
- `corridorCandidatesAdjacent(left, right)` — the pairwise adjacency test described above; the same axis, lane-gap, and overlap thresholds that back the union-find clustering.
- `collectCorridorCandidates(routes)` — turns every route's consecutive point pairs into `CorridorCandidate`s (`linkId`, `axis`, `perpendicular` coordinate, along-axis `start`/`end`, `direction` from the existing `chevronDirection` helper — corridor lane direction deliberately reuses the phase-3 chevron direction type rather than inventing a parallel enum, so opposite-direction lanes inside one bidirectional corridor are labeled exactly like their own chevrons — and the literal `from`/`to` points).
- `buildCorridor(candidates)` — assembles one cluster's deduplicated, ranked `MapCorridorLane`s, the corridor's `band`/`extent`, and the per-link segment map used for offsetting.
- `attachRoutingCorridors(routes, allRects)` — calls `computeBuiltCorridors`, then for every corridor lane: writes the `MapCorridorAssignment` onto the member route's `corridor` field exactly as phase 4 originally did (a route absent from every corridor keeps `corridor: null`), and — at most once per route, tracked via a `Set` so a route that is a member of two different corridor clusters at once (common; see below) is never offset twice in the same pass — attempts `applyCorridorLaneOffset` to actually move that lane's shared segment. `allRects` is every document's and folder's absolute rectangle (`Object.values(rectangles)` from `routeMapLinks`), used by the offset's obstacle-safety check.
- `applyCorridorLaneOffset(route, linkId, corridor, lane, segment, allRects, routes)` — computes `delta = (laneIndex - (laneCount - 1) / 2) * CORRIDOR_LANE_OFFSET` (4px per lane step, centered on the original centerline so a corridor's own extent doesn't drift), locates `segment.from`/`segment.to` as an exact consecutive pair in the route's current `points` (`findSegmentIndex`), then shifts both endpoints perpendicular to the corridor's axis (`y` for a horizontal corridor, `x` for a vertical one) and rewrites them in place — but only after every one of these gates passes; any single failure leaves that route's points completely untouched for this corridor (metadata still gets written; only the geometry offset is skipped):
  - the segment must have both a predecessor and a successor point in the route (never the route's very first or last point, i.e. never a `MapPort` location);
  - neither neighboring point may be exactly a `boundaryGateway.point` — a corridor segment immediately adjacent to a folder-boundary crossing is left unshifted entirely, because a small perpendicular nudge there can flip which side of the boundary the neighboring point falls on (moving it from "just inside the folder" to "just outside") without re-invoking the obstacle-aware `ZoneRouter` that originally produced it, which would silently break `assertFolderGatewayPolicy`'s inside/outside-neighbor invariant;
  - the two connecting segments (`prev`→shifted-from and shifted-to→`next`) must remain axis-aligned (`segmentAligned`) — true by construction for a genuine mid-route corridor segment, since the router's orthogonal-segment alternation means a neighbor is always perpendicular to it, but checked explicitly rather than assumed;
  - neither connecting segment may collapse to zero length (`pointsEqual`) — guards the case where a route already offset by an *earlier* corridor in this same pass (see the at-most-once note above) has a short pre-existing jog whose length exactly matches this corridor's own delta, which would otherwise silently merge two distinct points;
  - the offset connecting/shifted segments must avoid the interior of every "foreign" rectangle (`foreignObstacles`/`segmentAvoidsInteriors`): a rect counts as foreign only if it did **not** already contain the segment's original, pre-shift endpoints (`containsPointInclusive`), which is what lets a lane move freely within the zone it already occupies (its own ancestor folders are automatically excluded) while still being blocked from cutting through an unrelated document or an unrelated sibling folder's rectangle — this is the specific gate that keeps `assertAvoidsDocumentInteriors` and `assertFolderGatewayPolicy`'s "never traverses an unrelated folder" check passing with lane-offset geometry in play;
  - the offset must not introduce a new real crossing against any other route's geometry (`introducesNewCrossing`, reusing the same `segmentCrossingPoint` predicate `attachCrossingGaps` is built on) — without this gate, offsetting a densely-packed fixture's lanes measurably increased real crossings (the `fan-converge` fixture went from 0 to over 150 real crossings across 20 edges in testing before this gate was added), which would have broken that fixture's existing "stay a readable, mostly crossing-free organized trunk" bound.
- `foreignObstacles(allRects, from, to)` / `containsPointInclusive(rect, point)` — the "which rectangles were not already part of this segment's own zone" filter described above.
- `introducesNewCrossing(from, to, ownLinkId, routes)` — checks a candidate offset segment against every other route's full point list for a genuine crossing.
- `segmentAligned(first, second)` / `pointsEqual(first, second)` / `findSegmentIndex(points, from, to)` / `segmentAvoidsInteriors(source, target, obstacles)` — the small geometry predicates the offset gates above are built from.

Because `computeGatewayRegions`/`computeRoutingCorridors` still only read geometry, they continue to compose transparently with phase 3: a crossing that happens to land on a corridor-member edge's segment is still detected and gap-owned exactly as `attachCrossingGaps` already describes. What changed is *when* that composition happens — `routeMapLinks` now runs `attachGatewayRegions` and `attachRoutingCorridors` (including its point offsetting) before recomputing every route's `chevrons` and before `attachCrossingGaps`, specifically so both of those geometry-reading passes always see the final, already-offset points rather than stale pre-offset ones.

### Bidirectional distinguishability

A corridor's per-lane `direction` (already computed in phase 4, reusing the chevron direction type) is exposed to rendering via `MapRoute.corridor.direction`/`MapCorridorAssignment.direction`, unchanged. [`MapRouteEdge`](../components/MapRouteEdge.svelte.md) is what actually uses it now: a corridor-member edge gets a `corridor` CSS class (slightly heavier stroke) plus, for the lane travelling in the corridor's "reverse" direction (`left` on a horizontal corridor, `up` on a vertical one), a `corridor-reverse` class (dashed stroke) — so opposite-direction traffic sharing one corridor is visually distinguishable beyond spatial offset alone, on top of each lane already being a fully independent path with its own arrowhead and chevrons. A `data-corridor={corridor.corridorId}` attribute is also emitted as a hook for a future, more elaborate per-corridor visual pass.

### Gateway convergence was attempted and reverted

Item 3 of this phase's original spec — converging a `MapGatewayRegion`'s member crossing points toward a small, shared set of coordinates by `laneIndex`, the same way corridor lanes now converge toward their centerline — was implemented as a bounded post-hoc point-shift with the same style of safety gates used for corridor offsetting (skip when the shift would misalign a connecting segment, skip when it would cross a foreign obstacle, bounds-check against the folder's own rectangle). It reliably broke real invariants in testing: `assertFolderGatewayPolicy`'s "exactly one of a gateway's two neighboring points is inside the folder" check failed, and in one fixture a shifted approach segment cut straight through an unrelated folder's rectangle (`link:0001 traverses unrelated folder:area-0/module-1`). The root cause is structural, not a tuning problem: a gateway's actual crossing point is the exact target `ZoneRouter.route` was asked to reach when the route was first built, and the short stub segments immediately on either side of it were produced by that specific obstacle-aware search — nudging the crossing point after the fact, without re-invoking `ZoneRouter` from the new target, can silently reintroduce exactly the obstacle/boundary violations `ZoneRouter` exists to prevent. This is precisely the risk phase 4's original "known limitation" note already flagged for widening gateway/port geometry. Given the choice between shipping a fake/cosmetic convergence and being honest that it isn't done, gateway convergence is **not implemented**: `regionId`/`laneIndex`/`laneCount` are still attached to every `MapBoundaryGateway` exactly as phase 4 first shipped them, and `GATEWAY_SPACING` is unchanged (`10`), so a gateway's rendered crossing point is pixel-identical to before this pass. A real fix would mean threading region/lane awareness into `routeGateway`/`gatewayPoint` *before* the `ZoneRouter` call that targets it (so the router itself routes to the converged point, the same way `applyCorridorLaneOffset` was ultimately made safe by working with the router's already-finished output instead of second-guessing it) — a genuine redesign of that part of the pipeline, and a candidate for a later phase rather than something safe to attempt inside this fix.

## Geometry helpers

- `appendRoute`, `compactPoints`, `deduplicatePoints`, `pushPoint` — join and normalize polylines.
- `inflateRect`, `insetRect`, `pointInsideRect` — obstacle/container geometry.
- `uniqueNumbers` — sorted coordinate grid.
- `segmentKey`, `gatewayKey` — stable grouping/usage keys (`portKey` is documented above, under lane allocation).
- `perpendicularCenter`, `centerX`, `centerY`, `oppositeSide` — side geometry.
- `entryBefore`, `compare` — deterministic heap/string ordering.

Invariants: all segments orthogonal/finite; unrelated document interiors are never crossed; duplicate/self links remain independent; boundary order follows hierarchy; every edge endpoint on a document resolves to a distinct `MapPort` — no two edges on the same node side, regardless of direction, ever share an `index`/point; a single genuinely unroutable link is skipped with a logged diagnostic rather than aborting `routeMapLinks` for the rest of the graph; a link that fails partway through a multi-zone route never leaves behind reservations for the zones it did successfully cross, so later links sharing those zones are never penalized or detoured for segments belonging to an edge that is never rendered; a route under `CHEVRON_MIN_ROUTE_LENGTH` always has zero `chevrons`, and every `MapChevron`'s `direction` always matches the axis/sign of the exact segment its `point` lies on (now checked against each route's final, post-corridor-offset points, since `chevrons` is recomputed after `attachRoutingCorridors` runs); a `crossingGaps` point is always strictly interior to both crossing segments, so it never coincides with a `MapPort`, a gateway point, or any other route corner (likewise checked against final geometry, since `attachCrossingGaps` now runs last); every `MapBoundaryGateway` in a finished `routeMapLinks` result always carries a real `regionId`/`laneIndex`/`laneCount` (the placeholder values never survive `attachGatewayRegions`); a `MapCorridor` never forms from fewer than `CORRIDOR_MIN_MEMBERS` distinct links, so two or three coincidentally parallel short edges never register as a highway (see the dedicated boundary test in `map-graph.test.mjs`); every `MapCorridorLane`/`MapGatewayLane` within one corridor or region owns a distinct `laneIndex`, and logical edges sharing a corridor or gateway region always remain independent `MapRoute`s with their own full point sequence — a corridor or region is a detected grouping, never a merge; `attachGatewayRegions` never changes a route's `points` or a gateway's `point` (gateway convergence was attempted and reverted — see above); `attachRoutingCorridors` *may* change a corridor member's own shared-segment points (`applyCorridorLaneOffset`), but only by an offset that has already passed every safety gate above, so document/folder-interior avoidance, folder-gateway inside/outside-neighbor correctness, and "no new real crossings" all still hold for the final, possibly-offset geometry — every phase 1/2/3 invariant in this file continues to hold for that final geometry, just not necessarily for the same literal point values `routeDescriptor` first produced.
