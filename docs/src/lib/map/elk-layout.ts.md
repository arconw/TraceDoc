# ELK Layout Adapter

Source: `src/lib/map/elk-layout.ts`.

Builds deterministic recursive compound placement with ELK, then invokes [`routing`](routing.ts.md) and emits Svelte Flow nodes/edges. Phase 5 wraps this in a bounded, deterministic layout/routing feedback loop: lay out, route, score the result with [`routing`](routing.ts.md)'s `computeRoutingCost`, and — only when the score shows genuine structural defects — retry with more generous ELK spacing, keeping whichever pass scored best.

## Contracts

- `MapNodeData` — folder/document label/path, degree, this document's `ports` (`MapPort[]`, from [`routing`](routing.ts.md)), emphasis, the currently traced edge ID (`activeEdgeId`), open/trace/trace-unmount callbacks.
- `MapFlowNode` — non-draggable folder/document node.
- `MapEdgeData` — orthogonal points, endpoint sides, this edge's own `sourcePort`/`targetPort`, gateways (each carrying its resolved gateway-region/lane, from [`routing`](routing.ts.md)), its `chevrons` (repeated direction markers, from [`routing`](routing.ts.md)), `crossingGaps` (points where this edge's own path must render a small visual gap because an unrelated edge crosses it), `corridor` (this edge's shared-highway lane assignment, or `null` when it is not part of any detected corridor), accessibility label, emphasis/trace callback.
- `MapFlowEdge` — nonselectable custom route edge.
- `ElkMapNode` — internal recursive layout node; may itself carry `layoutOptions` (phase 5: the high-degree-node priority hint, see below) that the parent `layoutFolder` call must fold into the child entry it actually sends to ELK, since ELK positions siblings from the _parent's_ `children` array, not from a node's own standalone options.
- `MapLayout` — final node/edge arrays.
- `MapLayoutOptions` — phase 5's caller-facing override, `{ maxIterations?: number }`. [`MapView`](../views/MapView.svelte.md) never passes this (it always wants the full feedback loop); it exists so tests can force `{ maxIterations: 1 }` — a single, unadjusted ELK pass — as an explicit baseline to compare the feedback-enhanced result against.

## Functions

### Layout/routing feedback loop (phase 5)

- `layoutMapGraph(graph, engine, options?)` — the bounded feedback loop. Computes per-document degree once (`computeNodeDegrees`), then runs up to `maxIterations` (`options.maxIterations`, clamped to `[1, LAYOUT_FEEDBACK_ITERATIONS]`; `LAYOUT_FEEDBACK_ITERATIONS` is `3`) layout passes via `layoutPass`, each at a larger `LAYOUT_SPACING_MULTIPLIERS` entry (`[1, 1.35, 1.75]` — iteration 0 is byte-identical to every pre-phase-5 spacing value, since `Math.round(value * 1) === value` for every constant `layoutOptions` scales). After each pass it scores the result with `measureLayoutCost`/`routing`'s `computeRoutingCost`, keeps the lowest-`total`-cost pass seen so far (`best`), and stops — before the iteration cap — at the first of:
  - `cost.structural === 0` — the layout already has no real crossings, node overlaps, edge-through-node violations, or ambiguous corridors; there is nothing structural left to fix, so further escalation would only add unnecessary spacing/canvas size for a purely cosmetic (bend/length) gain. This is the common case: every fixture in `ROUTING_FIXTURES` except `fan-out`, `mixed-hub`, and the phase-5 `dense-skip-chain` fixture already scores `structural: 0` on iteration 0 alone, so `layoutMapGraph` runs exactly one pass for them — identical output to the pre-phase-5 single-pass code path;
  - the current iteration's `cost.total` did not improve on the previous iteration's (`!improved`, only checked once at least one escalated pass has run — `iteration > 0`) — "quality stopped improving," so escalating further is not expected to help either (confirmed empirically: on `fan-out`/`mixed-hub`, wider spacing spreads the fan-in/out endpoints further apart and _increases_ real crossings near the hub's own port cluster, so those two fixtures correctly stop after one escalated attempt and keep iteration 0's — the better — result as `best`);
  - the elapsed wall-clock time (`performance.now() - startedAt`) reaches `LAYOUT_FEEDBACK_TIME_BUDGET_MS` (`4000`) — a safety valve against a pathological graph, not a decision the score/output depends on in any test-observable way: every fixture this repo exercises finishes in well under a second, so this bound is never actually hit in practice and never changes which iteration wins.

  Returns `best.layout` — never a worse-scoring layout than a single unadjusted pass, since iteration 0 always seeds `best` first. `layoutMapGraph` itself does not catch a rejected `engine.layout()` call (e.g. from [`MapView`](../views/MapView.svelte.md)'s `elk.terminateWorker()` on cancellation) at any point in the loop — the rejection propagates out of whichever `await` it interrupted exactly as it did before phase 5's loop existed, so a cancelled/superseded layout request still cannot produce a `best.layout` at all, and [`MapView`](../views/MapView.svelte.md)'s existing request-ID gating (`completeMapLayout`/`failMapLayout` only applying when `requestId === session.requestId`) is never bypassed — see "Cancellation and staleness" below.

- `layoutPass(graph, engine, degrees, spacingMultiplier)` — one full layout: lays out every root folder in parallel at the given spacing multiplier, positions the root folders themselves, then converts to flow nodes/edges via `elkGraphToFlow` (which is what actually calls `routing`'s `routeMapLinks`). Identical in shape to what `layoutMapGraph` did directly, pre-phase-5, minus the multi-iteration wrapping.
- `measureLayoutCost(layout)` — adapts one `MapLayout` into `routing.computeRoutingCost`'s inputs: builds a `Record<linkId, MapRoute>` directly from `layout.edges` (each `MapFlowEdge.data` is structurally a superset of `MapRoute` — same `points`/`sourcePort`/`targetPort`/`boundaryGateways`/`chevrons`/`crossingGaps`/`corridor` fields — so no separate route reconstruction is needed), and a `Record<documentId, MapRect>` via `routing`'s exported `absoluteRectangles(layout.nodes)`, filtered to `kind === 'document'` nodes only (folder rectangles are deliberately excluded — see `routing.ts.md`'s cost-function section for why).
- `computeNodeDegrees(graph)` — total in+out degree per document, computed once per `layoutMapGraph` call directly from `graph.links` (independent of `linkCounts`, which `elkGraphToFlow` computes per-pass from the same source for a different purpose — the two are not unified because `computeNodeDegrees` must exist _before_ the first ELK pass even runs, to seed that very pass's high-degree hint).

### High-degree hub bias (phase 5)

Node degree influences placement in exactly one place: `buildDocumentNode(graph, documentId, degrees)` sets `layoutOptions: { 'elk.priority': String(degree) }` (capped at `999`) on any document whose total degree is at least `HIGH_DEGREE_THRESHOLD` (`8` — the same threshold this file's `layoutOptions()` already passed to ELK's own `elk.layered.highDegreeNodes.threshold`, so "high-degree" means the same thing to both ELK's built-in handling and this hint). `elk.priority` is a real, general-purpose ELK layout option (`org.eclipse.elk.priority`) that the layered algorithm's crossing-minimization and node-placement strategies use as a tie-breaker/weight; `layoutFolder`'s `children.map(...)` call folds this hint into the child entry it sends to ELK (`{ 'elk.portConstraints': 'FIXED_SIDE', ...hints }`) rather than discarding it, since ELK reads a node's layout options from the parent's own `children` array. This is the "bias initial placement... via ELK layout option hints keyed on degree" option the parent issue names explicitly; it runs unconditionally on every pass (not only escalated ones) since it costs nothing and does not risk the "quality stops improving" stopping condition.

No separate deterministic post-layout nudge was implemented on top of this: the general spacing-escalation loop above already re-lays-out (and can reposition) a high-degree node's whole neighborhood whenever that node's placement is part of what is producing structural cost, so a dedicated relocation step would duplicate the same mechanism for a narrower case. A hub whose _only_ problem is its raw corner position (no crossings, no overlap it is contributing to) is intentionally left as ELK placed it — `cost.structural === 0` in that case, and phase 5's own principle ("prefer space over ambiguity") does not licence moving a node for no measurable readability gain.

### Cancellation and staleness

The feedback loop adds no new cancellation mechanism and needs none: [`MapView`](../views/MapView.svelte.md)'s existing scheme — bump `layoutVersion`, call `elk.terminateWorker()`, replace `elk` with a fresh `ELK` instance, and gate every terminal `layoutSession` transition on `requestId === session.requestId` — already treats one `layoutMapGraph(graph, elk)` call as an opaque, cancellable unit of work regardless of how many internal `engine.layout()` calls it makes. Terminating the worker rejects whichever `engine.layout()` call is in flight (iteration 0, 1, or 2), that rejection propagates up through `layoutPass` → `layoutMapGraph` uncaught, and `updateLayout`'s `catch` block discards it via the same `version !== layoutVersion` check it already used before phase 5 — a cancelled request can reach at most a rejected promise, never a `best.layout` return value, whether it is cancelled during the first pass or the third. This was verified by re-running every pre-existing layout-session/request-queue test (`cancels active layout work and starts only the latest queued job`, `routes retry through cancellation for hide and signature changes`, `exposes edge controls only for the current successful layout`) unmodified against the phase-5 code; all pass, and none needed a phase-5-specific addition, matching the routing/readability epic's stated policy that generic session-level cancellation coverage does not need a fixture-specific duplicate.

## Functions (unchanged from phases 1–4)

- `elkGraphToFlow(graph, layout)` — recursively converts geometry, counts degrees, routes links, attaches each document's own ports, and builds flow records.
- nested `visit(children, parentId)` — preserves compound parent relationships.
- `mapHandleId(port)` — the single place a `MapPort` becomes a Svelte Flow handle ID (`<direction>-<side>-<index>`); shared by the edge's `sourceHandle`/`targetHandle` here and by [`MapDocumentNode`](../components/MapDocumentNode.svelte.md)'s own `Handle` rendering, so the two always agree.
- `attachDocumentPorts(nodes, routes)` — after routing, groups every route's `sourcePort`/`targetPort` by `documentId` and writes each document node's own `data.ports`, sorted by side then index then direction for stable iteration; a document with no incident edges gets an empty array.
- `layoutFolder(graph, folderId, engine, degrees, spacingMultiplier)` — bottom-up child-folder/document placement with header/padding; phase 5 threads `degrees` (for the high-degree hint) and `spacingMultiplier` (for `layoutOptions`) through the recursion.
- `layoutRootFolders(folders, engine, spacingMultiplier)` — positions multiple top-level containers; phase 5 threads `spacingMultiplier` through to its own `layoutOptions` call.
- `layoutEdgesForFolder(graph, folderId)` — deduplicates layout-only direct-child constraints.
- `directChildForDocument(graph, folderId, documentId)` — maps a deep document to the immediate child block at a layout level.
- `buildDocumentNode(graph, documentId, degrees)` — derives bounded width from title length; phase 5 adds the high-degree `layoutOptions` hint described above.
- `layoutOptions(spacingMultiplier)` — deterministic rightward layered ELK configuration and spacing; phase 5 scales every numeric spacing constant by `spacingMultiplier` via a local `scaled(value)` helper (`String(Math.round(value * spacingMultiplier))`), everything else unchanged.
- `fixedSidePorts(nodeId)` — declares top/right/bottom/left ELK ports (compound-layout placement only; unrelated to the visual `MapPort` model above).
- `linkCounts(graph, field)` — computes incoming/outgoing degree.

Invariants: ELK places blocks; custom routing owns final edge geometry and the port model built on top of it. `layoutMapGraph` never returns a layout scoring worse (by `computeRoutingCost`'s `total`) than a single unadjusted ELK pass over the same graph; identical graph input still produces identical output across repeated calls (no randomness or wall-clock-dependent branching in the score/adjustment decisions themselves — `performance.now()` is read only for the iteration-budget safety valve, which no exercised fixture ever reaches); a cancelled or superseded `layoutMapGraph` call can never resolve to a value the UI observes, regardless of which feedback iteration it was cancelled during.
