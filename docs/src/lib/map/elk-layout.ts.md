# ELK Layout Adapter

Source: `src/lib/map/elk-layout.ts`.

Builds deterministic recursive compound placement with ELK, then invokes [`routing`](routing.ts.md) and emits Svelte Flow nodes/edges. Phase 5 wraps this in a bounded, deterministic layout/routing feedback loop: lay out, route, score the result with [`routing`](routing.ts.md)'s `computeRoutingCost`, and — only when the score shows genuine structural defects — retry with more generous ELK spacing, keeping whichever pass scored best.

## Contracts

- `MapNodeData` — folder/document label/path, degree, this document's `ports` (`MapPort[]`, from [`routing`](routing.ts.md)), emphasis, the currently traced edge ID (`activeEdgeId`), open/trace/trace-unmount callbacks.
- `MapFlowNode` — non-draggable folder/document node.
- `MapEdgeData` — orthogonal points, endpoint sides, this edge's own `sourcePort`/`targetPort`, gateways (each carrying its resolved gateway-region/lane, from [`routing`](routing.ts.md)), its `chevrons` (repeated direction markers, from [`routing`](routing.ts.md)), `crossingGaps` (points where this edge's own path must render a small visual gap because an unrelated edge crosses it), `corridor` (this edge's shared-highway lane assignment, or `null` when it is not part of any detected corridor), accessibility label, emphasis/trace callback.
- `MapFlowEdge` — nonselectable custom route edge.
- `ElkMapNode` — internal recursive layout node.
- `MapLayout` — final node/edge arrays.
- `MapLayoutOptions` — phase 5's caller-facing override, `{ maxIterations?: number }`. [`MapView`](../views/MapView.svelte.md) never passes this (it always wants the full feedback loop); it exists so tests can force `{ maxIterations: 1 }` — a single, unadjusted ELK pass — as an explicit baseline to compare the feedback-enhanced result against.

## Functions

### Layout/routing feedback loop (phase 5)

- `layoutMapGraph(graph, engine, options?)` — the bounded feedback loop. Computes per-document degree once (`computeNodeDegrees`), then runs up to `maxIterations` (`options.maxIterations`, clamped to `[1, LAYOUT_FEEDBACK_ITERATIONS]`; `LAYOUT_FEEDBACK_ITERATIONS` is `3`) layout passes via `layoutPass`, each at a larger `LAYOUT_SPACING_MULTIPLIERS` entry (`[1, 1.35, 1.75]` — iteration 0 is byte-identical to every pre-phase-5 spacing value, since `Math.round(value * 1) === value` for every constant `layoutOptions` scales), with high-degree model-order promotion off (`promoteHighDegree: false`) throughout this sweep. After each pass it scores the result with `measureLayoutCost`/`routing`'s `computeRoutingCost`, keeps the lowest-`total`-cost pass seen so far (`best`, now `{ layout, cost }` rather than just `{ layout, total }` so the hub-reorder step below can read `best.cost.structural` without recomputing it), and stops — before the iteration cap — at the first of:
  - `cost.structural === 0` — the layout already has no real crossings, node overlaps, edge-through-node violations, or ambiguous corridors; there is nothing structural left to fix, so further escalation would only add unnecessary spacing/canvas size for a purely cosmetic (bend/length) gain. This is the common case: most fixtures in `ROUTING_FIXTURES` already score `structural: 0` on iteration 0 alone, so `layoutMapGraph` runs exactly one pass for them — identical output to the pre-phase-5 single-pass code path;
  - the current iteration's `cost.total` did not improve on the previous iteration's (`!improved`, only checked once at least one escalated pass has run — `iteration > 0`) — "quality stopped improving," so escalating spacing further is not expected to help either (confirmed empirically: on `fan-out`/`mixed-hub`, wider spacing spreads the fan-in/out endpoints further apart and _increases_ real crossings near the hub's own port cluster, so those two fixtures correctly stop after one escalated attempt and keep iteration 0's — the better — result as `best`);
  - the elapsed wall-clock time (`performance.now() - startedAt`) reaches `LAYOUT_FEEDBACK_TIME_BUDGET_MS` (`4000`) — see "Determinism risk from the wall-clock time budget" below; this is **not** a purely theoretical safety valve that never fires.

  After the spacing sweep, if `maxIterations > 1` and `best.cost.structural > 0` — meaning the graph still has genuine structural defects the spacing sweep alone could not resolve — `layoutMapGraph` calls `attemptHubReorder` for one further, bounded escalation attempt described below. Returns `best.layout` — never a worse-scoring layout than a single unadjusted pass, since iteration 0 always seeds `best` first and every later candidate (spacing or hub-reorder) only replaces it on strict improvement. `layoutMapGraph` itself does not catch a rejected `engine.layout()` call at any point in the loop — see "Cancellation and staleness" below for what actually happens when a layout is cancelled.

- `attemptHubReorder(graph, engine, degrees, best, startedAt)` — the dedicated hub-placement escalation step (see "High-degree hub bias" below for why it is separate from the spacing sweep above). Tries up to two further deterministic passes, one at each of `HUB_REORDER_SPACING_MULTIPLIERS` (`[1, 1.75]` — the spacing sweep's own first and last multipliers), each with `promoteHighDegree: true`, stopping early if the wall-clock budget is already exhausted. Keeps whichever of `best` and these extra candidates scores lowest `cost.total`; since it only ever replaces `best` on strict improvement, it can only make the final result at least as good as the plain spacing sweep already found, never worse.
- `layoutPass(graph, engine, degrees, spacingMultiplier, promoteHighDegree?)` — one full layout: lays out every root folder in parallel at the given spacing multiplier and promotion flag, positions the root folders themselves, then converts to flow nodes/edges via `elkGraphToFlow` (which is what actually calls `routing`'s `routeMapLinks`).
- `measureLayoutCost(layout)` — adapts one `MapLayout` into `routing.computeRoutingCost`'s inputs: builds a `Record<linkId, MapRoute>` directly from `layout.edges` (each `MapFlowEdge.data` is structurally a superset of `MapRoute` — same `points`/`sourcePort`/`targetPort`/`boundaryGateways`/`chevrons`/`crossingGaps`/`corridor` fields — so no separate route reconstruction is needed), and a `Record<documentId, MapRect>` via `routing`'s exported `absoluteRectangles(layout.nodes)`, filtered to `kind === 'document'` nodes only (folder rectangles are deliberately excluded — see `routing.ts.md`'s cost-function section for why).
- `computeNodeDegrees(graph)` — total in+out degree per document, computed once per `layoutMapGraph` call directly from `graph.links` (independent of `linkCounts`, which `elkGraphToFlow` computes per-pass from the same source for a different purpose — the two are not unified because `computeNodeDegrees` must exist _before_ the first ELK pass even runs, to seed the hub-reorder step's promotion).

### High-degree hub bias

`77b9644` originally set `layoutOptions: { 'elk.priority': String(degree) }` on every high-degree document, intending `org.eclipse.elk.priority` to bias ELK's placement. Code review traced elkjs's actual source (`node_modules/elkjs/lib/elk-worker.js`): the layered algorithm only ever reads this property in `SimpleRowGraphPlacer.sortComponents`, which `SimpleRowGraphPlacer.combine` only calls when there is more than one connected component to place (`components.size_1() == 1` returns immediately beforehand) — and this file's own `layoutOptions()` sets `elk.separateConnectedComponents: 'false'`, so the whole graph is always one component and `sortComponents` never runs. The hint was verified dead: re-running `layoutMapGraph` before/after `77b9644` on `fan-in`/`fan-out`/`mixed-hub` produced byte-identical node positions and edge geometry. It has been removed; `buildDocumentNode` and `ElkMapNode` no longer set or carry any per-node `layoutOptions` at all.

The real mechanism now is degree-based **model-order promotion**, applied only inside `attemptHubReorder` (not on the ordinary spacing sweep — see below for why):

- `promoteHighDegreeDocuments(documents, degrees)` reorders one folder's document list — the same array `layoutFolder` sends to ELK as `children` — so that every document whose degree is at least `HIGH_DEGREE_THRESHOLD` (`8`) comes first, sorted by degree descending then id ascending for a deterministic tie-break, followed by every other document in its original (already-alphabetical, from [`routing-fixtures.ts`](routing-fixtures.ts.md)-style callers, or otherwise caller-determined) order unchanged.
- This reordering is real and traced, unlike the removed hint: `elk-worker.js`'s `ElkGraphImporter` assigns each node's internal `modelOrder` property as its index in the `children` array it was given (`$setProperty_1(elknode, MODEL_ORDER_2, valueOf_3(index_0++))`), and `layoutOptions()` already sets `elk.layered.considerModelOrder.strategy: 'NODES_AND_EDGES'` (present since before this phase, for an unrelated reason), which makes the layered algorithm's crossing-minimization phase seed and bias its initial node ordering from that same `modelOrder` (`ModelOrderNodeComparator`, `SORT_BY_INPUT_ORDER_OF_MODEL`) — with no dependency on `separateConnectedComponents` at all. Feeding a high-degree node earlier in `children` measurably changes where ELK's crossing-minimization heuristic settles it within its layer.
- It is deliberately **not** applied unconditionally on every pass the way the old (dead) hint was. Empirically, reordering a folder's model order changes which local optimum ELK's greedy crossing-minimization heuristic converges to — sometimes better, sometimes measurably worse, for graphs that don't actually have a hub-in-corner problem. Applying it on the spacing sweep's own iterations (in place of, or blended with, wider spacing) was tried and rejected: on at least one constructed test graph it caused the spacing sweep to settle for a worse local optimum than plain spacing escalation alone would have found, which would have been a genuine regression versus pre-`77b9644` behavior for that shape of graph. Running it only as an additional, separate candidate after the spacing sweep already completed — keeping it only when it strictly beats whatever the spacing sweep already found — avoids that risk entirely while still fixing the corner case spacing alone cannot: `HUB_REORDER_SPACING_MULTIPLIERS`'s two attempts (base and widest spacing, both with promotion on) are pure additions to the candidate pool `best` is chosen from, never a replacement for the spacing-only candidates already evaluated.
- Verified on the new `hub-in-corner` fixture (see [`routing-fixtures.ts.md`](routing-fixtures.ts.md)): a single unadjusted ELK pass pins the fixture's 8-degree hub at the extreme edge of its layer (a corner-distance fraction of `1.00`, `structural` cost `3600`); `attemptHubReorder` moves it to a fraction of about `0.40` and cuts `structural` cost to `1500` (`map-graph.test.mjs`'s `moves a high-degree hub out of a bad corner...` case). Every fixture in `ROUTING_FIXTURES` that has no document at or above `HIGH_DEGREE_THRESHOLD` is provably unaffected, since `promoteHighDegreeDocuments` only ever reorders documents that clear that threshold and leaves every other document's relative order untouched.

### Cancellation and staleness

The feedback loop adds no new cancellation mechanism and needs none, but the mechanism it relies on is not what an earlier version of this document claimed. [`MapView`](../views/MapView.svelte.md)'s scheme is: bump `layoutVersion`, call `elk.terminateWorker()`, replace `elk` with a fresh `ELK` instance, and gate every terminal `layoutSession` transition on `requestId === session.requestId`. `terminateWorker()` (`node_modules/elkjs/lib/elk-api.js`) does nothing but `this.worker.terminate()` — it never touches the `PromisedWorker`'s pending `resolvers`, so whichever `engine.layout()` call was in flight (inside `layoutPass`, at any iteration or inside `attemptHubReorder`) is neither resolved nor rejected; its promise simply hangs forever, and the `await` inside `layoutPass`/`layoutMapGraph` that was waiting on it never resumes. Safety comes entirely from the fact that a hung promise can never produce a `best.layout` return value for [`MapView`](../views/MapView.svelte.md) to observe in the first place, combined with `updateLayout`'s existing `version !== layoutVersion` gate discarding anything that _does_ eventually resolve from a superseded request. This was verified by re-running every pre-existing layout-session/request-queue test (`cancels active layout work and starts only the latest queued job`, `routes retry through cancellation for hide and signature changes`, `exposes edge controls only for the current successful layout`) unmodified; all pass, and none needed a phase-5-specific addition — this is pre-existing elkjs/`MapView` behavior, not something phase 5 changed.

### Determinism risk from the wall-clock time budget

The `elapsed >= LAYOUT_FEEDBACK_TIME_BUDGET_MS` (`4000`) check in `layoutMapGraph`'s main loop, and the matching check in `attemptHubReorder`, are the one place this feedback pass's decision of "how many iterations to run" depends on something other than the deterministic graph input — wall-clock time, which varies with machine speed and load. This was measured, not assumed: a single unadjusted ELK pass (`maxIterations: 1`) over `map-graph.test.mjs`'s existing "500 documents, 1000 links" stress fixture already takes roughly 4.4 seconds on ordinary development hardware — meaning the 4000ms budget is already at or past its limit after just the _first_ pass for the largest fixture this repo already exercises, and the full feedback loop for that fixture returns the exact same result as `maxIterations: 1` because the time check cuts off further escalation before iteration 1 even starts. A prior version of this document claimed "every fixture this repo exercises finishes in well under a second, so this bound is never actually hit in practice" — that claim was false for this fixture and has been corrected.

This is a real, deliberate, bounded risk, left unfixed for now:

- **Bounded**: regardless of timing, `layoutMapGraph` can only ever produce a small, fixed set of candidate layouts (at most 3 spacing passes plus up to 2 hub-reorder passes), and always returns whichever of the candidates it actually computed scored best — it can never return something worse than a single unadjusted pass, and a run that gets cut short by the time budget simply explores fewer of those candidates rather than producing a wrong or corrupt result.
- **Not fully deterministic for large graphs**: two runs of the identical large graph on machines (or under load) that finish the first ELK pass on different sides of the 4000ms mark can genuinely explore a different number of candidates and therefore return different (though each individually valid, non-regressing) layouts. Every fixture below roughly 100 documents finishes in well under a second and is unaffected; this is a large-graph-only risk.
- **A larger budget was considered and rejected as the fix here**: raising `LAYOUT_FEEDBACK_TIME_BUDGET_MS` enough to comfortably clear the measured ~4.4s single-pass cost for the 500-document fixture (to make the valve a true "this should never happen" backstop, as the parent issue would prefer) would let the loop attempt the full 3-spacing-plus-2-hub-reorder candidate set for large graphs — up to roughly 5× the single-pass cost, i.e. tens of seconds — which risks both a visibly slower map view for large workspaces and breaking `map-graph.test.mjs`'s existing `completedAt - started < 8_000` bound for that same fixture. A genuine fix would need to decouple "how many escalation iterations to attempt" from wall-clock time entirely (for example, a fixed iteration budget that scales with graph size instead of a shared millisecond ceiling), which is a larger change than this defect fix and is left for a future phase; until then, this remains a known, accepted, non-catastrophic risk rather than a silently unstated one.

## Functions (unchanged from phases 1–4)

- `elkGraphToFlow(graph, layout)` — recursively converts geometry, counts degrees, routes links, attaches each document's own ports, and builds flow records.
- nested `visit(children, parentId)` — preserves compound parent relationships.
- `mapHandleId(port)` — the single place a `MapPort` becomes a Svelte Flow handle ID (`<direction>-<side>-<index>`); shared by the edge's `sourceHandle`/`targetHandle` here and by [`MapDocumentNode`](../components/MapDocumentNode.svelte.md)'s own `Handle` rendering, so the two always agree.
- `attachDocumentPorts(nodes, routes)` — after routing, groups every route's `sourcePort`/`targetPort` by `documentId` and writes each document node's own `data.ports`, sorted by side then index then direction for stable iteration; a document with no incident edges gets an empty array.
- `layoutFolder(graph, folderId, engine, degrees, spacingMultiplier, promoteHighDegree?)` — bottom-up child-folder/document placement with header/padding; threads `degrees` and `promoteHighDegree` (see "High-degree hub bias" above) and `spacingMultiplier` (for `layoutOptions`) through the recursion. Builds each folder's document list via `buildDocumentNode`, then, only when `promoteHighDegree` is true, reorders it with `promoteHighDegreeDocuments` before folding it into `children` alongside the already-positioned child folders.
- `layoutRootFolders(folders, engine, spacingMultiplier)` — positions multiple top-level containers; threads `spacingMultiplier` through to its own `layoutOptions` call.
- `layoutEdgesForFolder(graph, folderId)` — deduplicates layout-only direct-child constraints.
- `directChildForDocument(graph, folderId, documentId)` — maps a deep document to the immediate child block at a layout level.
- `buildDocumentNode(graph, documentId)` — derives bounded width from title length; carries no per-node `layoutOptions` (the dead `elk.priority` hint has been removed — see "High-degree hub bias" above).
- `promoteHighDegreeDocuments(documents, degrees)` — the degree-based model-order reorder described above: high-degree documents first (degree descending, id ascending tie-break), everything else in its original order.
- `layoutOptions(spacingMultiplier)` — deterministic rightward layered ELK configuration and spacing; scales every numeric spacing constant by `spacingMultiplier` via a local `scaled(value)` helper (`String(Math.round(value * spacingMultiplier))`), everything else unchanged. `elk.layered.considerModelOrder.strategy: 'NODES_AND_EDGES'` here is what makes `promoteHighDegreeDocuments`'s reordering actually matter to ELK's crossing minimization.
- `fixedSidePorts(nodeId)` — declares top/right/bottom/left ELK ports (compound-layout placement only; unrelated to the visual `MapPort` model above).
- `linkCounts(graph, field)` — computes incoming/outgoing degree.

Invariants: ELK places blocks; custom routing owns final edge geometry and the port model built on top of it. `layoutMapGraph` never returns a layout scoring worse (by `computeRoutingCost`'s `total`) than a single unadjusted ELK pass over the same graph. Identical graph input produces identical output across repeated calls for every fixture this repo exercises below roughly 100 documents; for large graphs (see "Determinism risk from the wall-clock time budget" above) the number of escalation candidates explored — and therefore, in principle, the exact result — can vary with wall-clock timing, a known and accepted risk rather than a silently unstated one. A cancelled or superseded `layoutMapGraph` call can never resolve to a value the UI observes (see "Cancellation and staleness" above), regardless of which feedback iteration it was cancelled during.
